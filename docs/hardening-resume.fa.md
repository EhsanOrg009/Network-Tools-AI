# ادامهٔ مأموریت امنیت و پایداری

تکمیل در ۲۰۲۶-۱۱-۱۱: خطای مستقیم `httpx.ReadTimeout` حین پیمایش stream بازتولید شد؛ برخلاف خطای شروع درخواست، SDK لزوماً آن را به `APITimeoutError` تبدیل نمی‌کند. اکنون همان `LLMTimeout` و cooldown اعمال می‌شود و درخواست دوم ارسال نمی‌شود. آزمون عدم ارسال تکراری و بسته‌شدن stream افزوده شد.

مبنای این اجرا `8f30c81` روی `master` در تاریخ ۲۰۲۶-۱۱-۱۰ است. ۲۵ commit اخیر و مستندات فازهای ۰ تا ۷ بازبینی شدند. پیاده‌سازی‌های سالم قبلی حفظ می‌شوند.

وضعیت اولیه: چهار فایل تغییرکردهٔ `llm_client.py`، `config.py`، `ai_activity.py` و `ai_analysis.py`؛ پوشهٔ `docs/benchmarks/` و فایل‌های `scripts/benchmark_ollama.py` و `tests/test_llm_reliability.py` ثبت‌نشده بودند. این‌ها ادامهٔ نیمه‌تمام فاز LLM هستند و پس از بازبینی و آزمون تکمیل می‌شوند. `run.txt` ثبت‌نشده بود و دست‌نخورده می‌ماند.

خط پایهٔ واقعی پیش از تغییر کد: `uv run pytest -q -rs`، **۴۶۴ موفق، ۴ skipped** در ۱۲۰٫۶۸ ثانیه؛ سه آزمون مدل نیازمند opt-in و چهارمی به‌دلیل نبود اتصال Ollama اجرا نشدند. Dashboard: **۲۲ موفق**؛ `npm run build` موفق. افزایش از مبنای تاریخی ۳۲۴/۳۳۶ عمدتاً مربوط به تست‌های سخت‌سازی commitشده و ۵ تست LLM موجود در working tree است. تست حذف یا ضعیف نشده است.

`uv 0.11.23`، `uv python list` و `uv sync --check` اجرا شدند: ۳۶ بسته هماهنگ، lockfile به‌روز و بدون تغییر لازم. هیچ بسته یا محیط Python تازه‌ای ایجاد نشد.

## فاز ۸ — پایداری درخواست مدل

کد نیمه‌تمام بازبینی شد: تفکیک timeout اتصال/تولید، حذف retry پنهان SDK، قفل تک‌درخواست روی LLM مشترک، cooldown بعد timeout، metadata مستقل برای threadها و بستن stream حفظ شدند. Structured Outputs بعد رد شدن provider خاموش نمی‌شود و در fallback پاسخ غیرstream هم ارسال می‌شود. خروجی با `finish_reason=length` یا قطع stream موفق تلقی نمی‌شود.

پیش‌فرض مدل `gemma-4-e4b:latest` است؛ `.env` کاربر تغییر نمی‌کند. مقادیر محافظه‌کارانهٔ پیشنهادی: batch=1، timeout تولید=600s، اتصال=5s، cooldown=60s، سقف خروجی=4096. این‌ها **تنظیم نهایی بهینه‌شده با مجموعهٔ کامل بنچمارک نیستند**. context سرویس تغییر نکرده است.

دو نتیجهٔ موجود از کار قبلی در `benchmarks/ollama-runtime.jsonl`: تک‌هشدار OpenAI سرد ۲۳۱٫۹۴ ثانیه، ورودی ۵۱۷ و خروجی ۱۲۱۰؛ تک‌هشدار native گرم ۱۲۸٫۲۹ ثانیه، ورودی ۵۱۷ و خروجی ۱۰۷۶. هر دو `stop`، schema معتبر و context گزارش‌شده ۴۰۹۶ دارند. درخواست سرد از timeout قبلی ۱۸۰ ثانیه بیشتر بوده است؛ این شاهد ناکافی‌بودن آن timeout برای حداقل یک درخواست است، نه اثبات علت همهٔ timeoutها. علت دقیق خطای گزارش‌شده با مجموع ۳۹۹۵ توکن هنوز نیازمند درخواست قابل بازتولید است.

در اجرای فعلی `ollama list/ps/show` حتی خارج sandbox به سرویس متصل نشد. CLI نسخهٔ 0.40.15 است؛ `nvidia-smi` با درایور ارتباط ندارد. RAM کل ۷٫۰ GiB و available حدود ۳٫۵ GiB؛ swap مصرف‌شده حدود ۱٫۶ GiB. وجود رکوردهای قبلی جایگزین آزمون زندهٔ فعلی نیست. سرویس سیستم یا درایور تغییر نکرد.

مستندات رسمی [context](https://docs.ollama.com/context-length)، [FAQ](https://docs.ollama.com/faq) و [OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility) خوانده شدند. VRAM کمتر از ۲۴ GiB معمولاً context پیش‌فرض 4K دارد؛ API native از `options.num_ctx` پشتیبانی می‌کند، اما API سازگار OpenAI تنظیم مستقیمی برای context ندارد و راه مستندشده Modelfile است. افزایش `max_tokens` معادل افزایش context نیست. تغییر ۶۱۴۴/۸۱۹۲ تا بررسی واقعی منابع انتخاب نشده است.

برای ادامهٔ آزمایش‌ها، اسکریپت موجود فقط شواهد ساختگی را به loopback می‌فرستد. ابتدا batch=1 و سپس 2 و 3؛ contextهای 4096، 6144 و 8192 باید ترتیبی و با بررسی حافظه آزمایش شوند. نمونه: `uv run python scripts/benchmark_ollama.py --case warm-single --context 4096 --batch 1`. برای truncation از `--budget 16` و برای timeout از `--timeout 1` استفاده شود؛ پس از timeout تا پایان generation قبلی درخواست بعدی ارسال نشود. آزمون‌های زندهٔ باقی‌مانده در گزارش نهایی صریحاً مشخص می‌شوند.

آزمون هدفمند نهایی فاز ۸: **۶۹ موفق** در ۳٫۸۱ ثانیه. اجرای نخست یک شکست داشت چون تست گروهی به پیش‌فرض batch=5 متکی بود؛ اندازهٔ گروه در همان تست صریح شد تا همچنان انتساب ID تکراری/ناشناخته در پاسخ گروهی را بررسی کند.

## فاز ۹ — کنترل تحلیل Security

مهاجرت افزایشی `003_security_ai_control` مقدار اولیهٔ OFF، شناسهٔ مستقل کار تحلیل، زمان retry، ورودی ماندگار خودکار و تاریخچهٔ تحلیل را اضافه می‌کند. رویداد و قصد تحلیل در همان تراکنش `insert_alert` ثبت می‌شوند. خاموش/روشن‌کردن با همان قفل تراکنش و Audit Log انجام می‌شود؛ timestamp قدیمی داخل رویداد باعث خروج آن از صف نمی‌شود. معیار، زمان دریافت است. دادهٔ تاریخی به‌صورت خودکار وارد صف نمی‌شود.

در معماری فعلی، منبع جدول Security مسیر `/api/alerts` است؛ تمام هشدارهای آن، از جمله شدت پایین و ناشناخته، واجد شرایط‌اند. دادهٔ packet، payload و تمام رکوردهای خام DNS/TLS/flow خودکار به مدل ارسال نمی‌شوند. ابزارهای موجود مشاهدهٔ eventها مستقل باقی می‌مانند.

`AI_ANALYSIS_ENABLED` تنها کلید فعال‌بودن worker است و با Auto Analysis فرق دارد. حالت خودکار فقط از API مدیر یا کلید بالای Security تغییر می‌کند و در دیتابیس می‌ماند. درخواست دستی فقط همان `alert_id` را با `job_id` مستقل ثبت می‌کند. کلیک تکراری، queued/processing/completed موجود را برمی‌گرداند. شکست اجازهٔ retry دارد؛ reanalyze عملیات جداگانه است. نتیجهٔ قبلی در `ai_analysis_history` حفظ و از API تاریخچه قابل دریافت است. کار دستی حتی وقتی batch بزرگ‌تر تنظیم شده، با ردیف‌های دیگر گروه‌بندی نمی‌شود.

پنجرهٔ آمادهٔ پردازش محدود است؛ مازاد خودکار در intake دیسکی حفظ و تدریجی منتقل می‌شود. درخواست دستی تازه در ظرفیت کامل 429 می‌گیرد؛ کلیک روی کار موجود همان کار را برمی‌گرداند. شمارش queued شامل intake هم هست. رفع گرسنگی صف پیش از LIMIT در SQL انجام می‌شود و امتیاز قدمت سقف ندارد؛ مشکل قدیمی که هشدار کم‌اولویت پشت ۵۰ کاندیدای پر‌اولویت گیر می‌کرد اصلاح شد.

پس از restart، PROCESSING با همان job_id و تأخیر محافظتی به PENDING برمی‌گردد؛ نتیجهٔ موفق دوباره اجرا نمی‌شود. عدم اتصال دارای backoff ماندگار و سقف تلاش هر دوره است؛ بعد از بازگشت واقعی مدل در probe فهرست مدل‌ها، دورهٔ قطع اتصال قابل بازیابی است. busy بودجهٔ تلاش را مصرف نمی‌کند. timeoutهای متوالی پس از سقف تلاش به retry صریح مدیر نیاز دارند؛ قطع ارتباط الزاماً به معنی پایان generation روی سرور نیست. worker هنگام shutdown از ثبت نتیجه روی اتصال بسته جلوگیری می‌کند.

رابط: OFF/ON واقعی، شمارش کل queued/processing/completed/failed، مدل، وضعیت اتصال و آخرین پردازش. وضعیت هر ردیف با ID همان صفحه خوانده می‌شود؛ حذف‌شدن از محدودیت فهرست ۵۰۰تایی دیگر باعث نمایش وضعیت جعلی نمی‌شود. شکست API تحلیل، هشدارها را پنهان نمی‌کند و «وضعیت نامشخص» نشان می‌دهد. صفحه وضعیت را poll می‌کند؛ صف‌بندی خودکار کاملاً Backend است.

آزمون هدفمند نهایی: **۱۴۱ موفق** در ۸٫۶۱ ثانیه، شامل مهاجرت از دیتابیس قدیمی، آزمون ۲۴ کلیک هم‌زمان، rollback حسابرسی و ingestion، OFF/ON، restart، ظرفیت و قطعی مدل. Dashboard: **۲۹ موفق** و build موفق. شکست‌های میانی مربوط به unpack نکردن tuple در fixture تازه و تکمیل‌نبودن مستندات endpointهای جدید بودند؛ هر دو اصلاح و دوباره آزموده شدند. ماتریس API بازتولید شد: ۷۷ مسیر تابعی به‌علاوهٔ OpenAPI و SPA.
