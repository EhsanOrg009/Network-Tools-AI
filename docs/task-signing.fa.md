# امضای نسخهٔ ۲ و مهاجرت عامل‌ها

وضعیت قبلی سرور از کلید مشتق‌شده استفاده می‌کرد، ولی عامل برای مشتق‌کردن آن کلید مادر را دریافت می‌کرد؛ بنابراین نفوذ به یک عامل می‌توانست نسخهٔ قدیمی سایر عامل‌ها را تهدید کند.

نسخهٔ ۲ از HMAC-SHA256 با کلید مستقل هر عامل استفاده می‌کند. دلیل حفظ الگوریتم متقارن، سازگاری اسکریپت تک‌فایلیِ فقط متکی به کتابخانهٔ استاندارد Python در Windows/Linux و نبود وابستگی رمزنگاری در پروژه است. پیاده‌سازی رمزنگاری اختصاصی اضافه نشده است. ریشهٔ تصادفی ۲۵۶ بیتی جدید مستقل از کلید قدیمی است؛ سرور آن را در `task-signing-v2.key` کنار دیتابیس با مجوز 0600 تولید می‌کند. حتی دانستن master قدیمی کلیدهای نسخهٔ ۲ را آشکار نمی‌کند. ریشه، token و کلید عامل در prompt مدل یا پاسخ مدیر نمایش داده نمی‌شوند.

عامل فعال با توکن خودش از `GET /api/agent/v1/signing-key` تنها کلید خودش را روی TLS می‌گیرد. کلید در فایل وضعیت 0600 ذخیره می‌شود؛ پاسخ `Cache-Control: no-store` دارد. کلید سرور را هرگز به Agent کپی نکنید. نسخهٔ جدید متغیر `NETAGENT_TASK_SIGNING_KEY` را استفاده نمی‌کند. HTTP فقط برای محیط تست با مجوز صریح محلی قابل استفاده است.

امضا به Agent ID، Task ID، نوع، digest تمام پارامترها، timeout، expiry، nonce، key_id و protocol_version بسته شده است. عامل جدید downgrade به نسخهٔ ۱ را رد می‌کند؛ task-id journal و nonce جلوی replay را می‌گیرند. revocation صدور کلید، heartbeat و dispatch جدید را قطع می‌کند. برای کاری که قبلاً تحویل شده و عامل کاملاً آفلاین است، لغو فوری از راه شبکه ممکن نیست؛ expiry و timeout دامنهٔ آن را محدود می‌کنند.

ترتیب استقرار:

1. ابتدا سرور را ارتقا دهید و فایل ریشهٔ نسخهٔ ۲ را مانند سایر secrets، خارج Git پشتیبان بگیرید.
2. عامل‌ها را تدریجی به `endpoint_agent.py` نسخهٔ `1.1.0` ارتقا دهید؛ ID و token فعلی حفظ می‌شوند. heartbeat قابلیت `task_signing_v2` را اعلام و کلید خودش را دریافت می‌کند.
3. نسخهٔ ۱ فقط تا deadline ماندگارِ `task_signing_legacy_deadline_epoch` در meta مجاز است. مقدار اولیه از `TASK_SIGNING_LEGACY_DAYS=30` می‌آید و restart آن را تمدید نمی‌کند.
4. پس از ارتقای عامل‌ها، `TASK_SIGNING_ALLOW_LEGACY=false` را روی سرور تنظیم کنید و متغیر قدیمی master را از تنظیم سرویس عامل‌ها حذف کنید. خاموش‌شدن امضای قدیمی heartbeat/inventory/diagnostics را قطع نمی‌کند.

تا پایان مهاجرت، عامل‌های نسخهٔ ۱ همچنان ریسک master مشترک را دارند؛ این محدودیت پنهان نشده است. برای قطع فوری آن می‌توان legacy را غیرفعال کرد، ولی اجرای مدیریتی عامل‌های ارتقانیافته متوقف می‌شود. این مأموریت تنظیم سرویس‌های عامل یا سیستم‌عامل را خودکار تغییر نمی‌دهد.

برای چرخش ریشهٔ نسخهٔ ۲، در پنجرهٔ نگهداری سرور را متوقف کنید، فایل ریشهٔ قبلی را در محل امن بایگانی و یک فایل تصادفی جدید ۳۲ بایتی به قالب hex با مجوز 0600 جایگزین کنید. پس از شروع سرور، heartbeat عامل جدید کلید جدید را می‌گیرد. پاکت‌های قبلی با کلید جدید معتبر نیستند؛ نتایج کارهای اجراشده همچنان با credential خود عامل قابل تحویل‌اند. credential ثبت‌نام یا ID عامل برای چرخش امضا تغییر نمی‌کند.
